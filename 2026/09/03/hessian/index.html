流程分析

跟我之前接触的fastjson，jackson最大的不同之处就是反序列化的时候不使用Getter和Setter，Hessian是通过反射赋值的方式实现的。

首先读取序列化数据的tag来判断类型，M对应的是Map/Object对象。在Hessian中普通Java对象是按照Map来处理的，这也可以理解，因为是通过反射来反序列化数据，需要的就是属性字段以及对应的值，也就是一个键值对所以按照Map来处理（我是怎么理解的）。

这个UnsafeDeserializer就是更高性能的反序列化器，它使用了sun.misc.Unsafe 类来反序列化。前面提到过Hessian使用反射来反序列化，JavaDeserializer确实是使用的反射，但UnsafeDeserializer不是。sun.misc.Unsafe这是一个更为底层的工具，他能像C/C++一样操作内存，所以说他走的Unsafe这个独特的路，性能更高。不过如果不支持Unsafe或者禁用的话就会用JavaDeserializer。

ROME

首先想到的是ROME链，但是这存在一个致命的问题。Hessian对于static和transient字段是不参与序列化和反序列化流程的，所以ROME链到TempaltesImpl以后就走不通了，因为_tfactory是transient字段，所以反序列化以后为null，这样就会有空指针的问题了。

所以要把TemplatesImpl这个部分改为JdbcRowsetImpl这样就能走通了。

值得一提的是ToStringBean的toString方法调用Getter的顺序是不可预测的，可能会出现像我这样还没有调用getDatabaseMetaData()就因为别的Getter缺少参数，抛异常从而中断for循环的情况。我因为这个问题jdbcRowSet.setMatchColumn("foo");添加了这一行。

还有一个问题是用IDEA调试的时候会出现每走一步都触发链子的情况，这是IDEA调试器的问题如下图把设置关了就行。

Apache Dubbo Hessian反序列化 CVE-2020-1948

因为Dubbo用的是Hessian2先看一下他跟Hessian的区别。

Hessian2中普通java对象和Map已经取分开了，普通java对象对应的是C，序列化数据的结构也发生了很大的改变。先来了解一下序列化数据结构变成什么样了。

User{name=’Alice’,id=100}对应的序列化数据如下

[ ‘C’ ] [ “com.example.User”, 2, “id”, “name” ] [ 0x60 ] [ 100 ] [ “Alice” ] 大体上是这样的

可以看到这个java对象的数据不再是以键值对的形式存在的。一步一步看，C表示类定义(后面再解释)，com.example.User是类的全名称，2表示后面有两个属性字段，0x60跟类定义有关，100和Alice是属性字段相对应的值。

首先发送端和接收端各自同步维护着存储类定义数据的表。0x60代表第一个类定义，0x61代表第二个类定义以此类推。预先准备好了16个空间，可以在switch case语句中看到。例如，第一次发送上面例子中的User对象的时候，类定义存储表还是空的，发送端会记录下这次发送的类定义，由于是第一个类定义序列化数据中添加0x60。接收端看到User是第一次接收的对象以后，也放到了自己的类定义存储表中，这样就实现了同步。第二次发送User对象的时候就不一样了，因为这个类定一已经存在了，只需要发送 [ 0x60 ] [ 101 ] [ “Tom” ]这样的数据就好了，接收端一看到0x60就知道这段数据对应的是User了。当类定义数量超过16个的时候就会进行扩容。

所以这段代码的第一个部分就是创建类定义，递归调用readObject，这样就会走到case: 0x60..这部分了，到这里就是赋值部分了。

反序列化HashMap的话跟Hessian差不多，他对应的是H。没什么变化还是会创建HashMap以后往里面将反序列化的键值对put进去。
